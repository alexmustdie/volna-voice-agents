# Volna – платформа голосовых ИИ-агентов

Volna is a voice AI agent platform: agents make outbound calls over a contact list and answer inbound calls in Russian. Stack: Python 3.12, FastAPI, async SQLAlchemy 2 + Alembic, PostgreSQL, Jinja2 admin panel, Twilio Media Streams for telephony, OpenAI GPT-Live-1 or Yandex Realtime as the voice engine, pytest. To run it locally in mock mode without any API keys: `cp .env.example .env && docker compose up --build`, then open http://localhost:8000.

Дальше по-русски: стек, архитектура, запуск, конфигурация и принятые решения. Заметки о ценах и
датах живых проверок вынесены в `docs/NOTES.md`.

## Стек

- Python 3.12, FastAPI, SQLAlchemy 2 (async), Alembic, PostgreSQL 16
- Панель управления: Jinja2-шаблоны (без сборки фронтенда)
- Голос: OpenAI GPT-Live-1 (`wss://api.openai.com/v1/live/sessions`), бэкенд-модель для рассуждений и function calling задаётся в конфиге (`BACKEND_MODEL`, по умолчанию `gpt-5.6-luna`)
- Телефония: Twilio Programmable Voice + Media Streams, за интерфейсом `app/telephony/base.py`
- docker-compose: `app` + `postgres`

## Архитектура

Приложение разбито на слои, у каждого внешнего контура есть интерфейс и мок-реализация, поэтому сквозной сценарий (кампания → воркер → звонок → транскрипт → встреча) прогоняется без сети и без секретов.

```
app/
  config.py, db.py, models.py, phone.py, prompts.py, security.py (токены медиа-сокетов)
  live/        голосовая сессия: base.py (LiveSession, LiveSessionConfig, LiveEvent),
               openai_live.py (GPT-Live-1 по WebSocket), yandex_live.py (Yandex Realtime),
               fake.py (мок), factory.py (выбор движка по голосу), bridge.py (мост телефония <-> сессия),
               g711.py (mu-law <-> PCM), voices.py (справочник голосов)
  telephony/   base.py (TelephonyProvider + get_provider), twilio_provider.py, fake_provider.py
  services/    calls.py (жизненный цикл звонка, инструменты агента, фоновый разбор), contacts.py (CSV),
               campaigns.py, quota.py (суточные лимиты), stats.py, analysis.py (разбор транскрипта
               после звонка), call_results.py и dnc.py (факты разговора, общие для инструментов и
               разбора), offers_client.py (клиент внешнего сервиса офферов)
  worker/      dialer.py (воркер обзвона)
  web/         routes.py (панель), twilio_routes.py (вебхуки и медиа-сокет), browser_call_routes.py
               (звонок из браузера), call_session.py (общий жизненный цикл звонка через WebSocket),
               fake_routes.py (симуляция), playback.py (учёт незаигранного звука), templates/, static/
alembic/       5 миграций
tests/         61 тест: юнит-тесты, сквозной прогон в мок-режиме, клиенты GPT-Live и Yandex Realtime
               против локального WebSocket-сервера, медиа-сокет Twilio, браузерный стенд
```

Слои и их интерфейсы:

1. `app/live` – голосовая сессия. `LiveSession` (`start`, `send_audio`, `send_tool_result`, `close`, `events`) нормализует протоколы OpenAI и Яндекса в единый поток `LiveEvent` (аудио, транскрипт, вызов инструмента, закрытие). `fake.py` играет роль модели в мок-режиме. `factory.py` выбирает движок по голосу агента.
2. `app/telephony` – провайдер телефонии. `TelephonyProvider` (`start_outbound_call`, `hangup`, `caller_number`), реализации `TwilioProvider` и `FakeProvider`; `get_provider()` подставляет мок при `FAKE_CALLS=true`.
3. `app/services` – бизнес-логика без привязки к HTTP: жизненный цикл звонка и обработка инструментов агента (`calls.py`), импорт CSV с нормализацией номеров, кампании, квоты, статистика, разбор звонка по транскрипту, клиент офферов.
4. `app/web` – FastAPI-роутеры: панель на Jinja2, вебхуки Twilio и WebSocket медиа-потока, тестовый звонок из браузера, маршруты симуляции.
5. `app/worker` – воркер обзвона: берёт контакты из очереди активных кампаний с учётом окна часов, лимита параллельных звонков и квот и запускает звонки через провайдера. Работает asyncio-задачей внутри приложения или отдельным процессом.

Мост `app/live/bridge.py` связывает слои 1 и 2: принимает аудио от провайдера, отдаёт его в сессию, возвращает ответ модели, обрабатывает перебивания и вызовы инструментов через `services/calls.py`. Жизненный цикл звонка поверх WebSocket (мост, чтение сокета, общий teardown) один для Twilio и браузерного стенда: `app/web/call_session.py`.

## Быстрый старт (мок-режим, без секретов)

```bash
cp .env.example .env
docker compose up --build
```

Панель: http://localhost:8000. `docker-compose.yml` поднимает приложение и свой PostgreSQL. В `.env.example` включён `FAKE_CALLS=true`: звонки и GPT-Live симулируются, внешние API не вызываются, деньги не тратятся.

Сценарий проверки:

1. Агенты → создать агента (имя, пол, возраст, голос, ниша, компания, цель, обязательные вопросы). Кнопка "промпт" показывает сгенерированные системные промпты.
2. Базы номеров → создать базу и загрузить CSV (`phone,name`, имя опционально, разделитель `,` или `;`). Номера нормализуются в E.164 (регион по умолчанию RU), дубликаты и мусор отсекаются.
3. Кампании → создать (агент, база, окно часов, дни недели, таймзона, лимит параллельных звонков 1–20) → на странице кампании "Запустить".
4. Воркер каждые `WORKER_POLL_SECONDS` берёт контакты в статусе `new`, соблюдая окно и лимит. В мок-режиме часть звонков "не дозванивается" (`FAKE_ANSWER_RATE`), часть заканчивается встречей (`FAKE_MEETING_RATE`), часть просьбой не звонить.
5. Страница кампании: прогресс, звонки, транскрипты, встречи. Дашборд: конверсия, средняя длительность, минуты.
6. Входящие → привязать номер к агенту → "симулировать входящий".

## Тест модели без телефонии

Страница "Тест в браузере" (`/test`): микрофон браузера → наш мост → голосовая модель с промптом агента, инструментами и записью результата в БД. Проверяется всё, кроме телефонии: промпт, голос, перебивания, вызов `book_meeting`, транскрипт. Нужны ключи движка агента в `.env` (значение `FAKE_CALLS` не важно); без ключей страница работает в мок-режиме. Открывать по `http://localhost:8000` (для микрофона браузеру нужен localhost или https). Сокет `/test/call` принимает только токен, выданный страницей (см. "Design decisions"). Тарифицируется как обычная сессия движка.

Образцы голосов (`/test/voices`) читаются из `app/web/static/voices/*.wav`; в репозитории каталог пустой, страница показывает только те файлы, которые есть.

## Локальная разработка без Docker

```bash
python -m venv .venv
.venv/Scripts/pip install -r requirements-dev.txt   # Windows; на Linux/macOS .venv/bin/pip
```

Для БД нужен PostgreSQL (`DATABASE_URL` в `.env`) либо для быстрой пробы SQLite:

```bash
DATABASE_URL=sqlite+aiosqlite:///./volna.db alembic upgrade head
DATABASE_URL=sqlite+aiosqlite:///./volna.db uvicorn app.main:app --reload
```

Тесты (73, мок-режим, включая проверку клиента GPT-Live против локального WebSocket-сервера, воспроизводящего документированный протокол, медиа-сокета Twilio, конкурентности и идемпотентности) и линтер:

```bash
.venv/Scripts/python -m pytest -q
.venv/Scripts/ruff check .
.venv/Scripts/ruff format --check .
```

По умолчанию тесты идут на SQLite (схема через `create_all`, отдельный файл на тест). Тесты, которым нужны блокировки строк (маркер `pg`, например два воркера разом), на SQLite пропускаются: она выполняет операторы по одному и гонку не воспроизводит. Чтобы прогнать всё на PostgreSQL, задайте `TEST_DATABASE_URL`: схема накатится миграциями (`alembic upgrade head`), между тестами таблицы очищаются `TRUNCATE ... RESTART IDENTITY`:

```bash
createdb volna_test
TEST_DATABASE_URL=postgresql+asyncpg://volna:volna@localhost:5432/volna_test .venv/Scripts/python -m pytest -q
```

CI (`.github/workflows/tests.yml`) на каждый push и pull request гоняет три job: линтер (`ruff check`, `ruff format --check`), тесты на SQLite и тесты на PostgreSQL 16 (сервис в job), где перед ними идут `alembic upgrade head` и `alembic check`: модели и миграции не должны расходиться.

## Реальный режим

1. Заполнить в `.env`: `SESSION_SECRET` (случайная строка не короче 16 символов, например `python -c "import secrets; print(secrets.token_hex(32))"`), `OPENAI_API_KEY`, `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_PHONE_NUMBER`, выставить `FAKE_CALLS=false`. Без `FAKE_CALLS=true` приложение считает режим реальным и при коротком `SESSION_SECRET` не стартует.
2. Приложение должно быть доступно из интернета по HTTPS (Twilio ходит в вебхуки и открывает WebSocket). Для разработки: `ngrok http 8000`, полученный URL записать в `PUBLIC_BASE_URL`.
3. Входящие: в консоли Twilio у номера задать Voice webhook `POST {PUBLIC_BASE_URL}/twilio/voice/inbound`, а в панели Volna (Входящие) привязать этот номер к агенту.
4. Исходящие вебхуки Twilio получает из параметров звонка автоматически (`/twilio/voice/outbound/{call_id}`, `/twilio/status/{call_id}`), настраивать не нужно.

Для сервера есть `docker-compose.prod.yml`: без своего PostgreSQL (`DATABASE_URL` в `.env` указывает на внешнюю базу), панель публикуется на `PANEL_BIND` (по умолчанию только localhost), наружу её должен отдавать reverse proxy с авторизацией. Запуск: `docker compose -f docker-compose.prod.yml up -d --build`.

Поток исходящего звонка: воркер → `TwilioProvider.start_outbound_call` → абонент ответил → Twilio запрашивает TwiML → `<Connect><Stream url="wss://.../twilio/media/{call_id}"><Parameter name="token" .../></Stream>` → Twilio открывает WebSocket с аудио G.711 mu-law 8 кГц и возвращает токен в событии `start` → `CallBridge` открывает сессию движка с `audio.format = audio/pcmu 8000` и мостит аудио в обе стороны → транскрипты и вызовы функций пишутся в БД → агент вызывает `end_call` → сокет закрывается, Twilio завершает звонок → звонок финализируется по итогу моста, status callback Twilio уточняет длительность.

## Голосовые движки

Движок выбирается переменной `VOICE_ENGINE`, оба реализуют один интерфейс `app/live/base.py`, мост и телефония от выбора не зависят.

| | `openai` (GPT-Live-1) | `yandex` (Yandex AI Studio Realtime) |
|---|---|---|
| Русский | неродной акцент (OpenAI: native только en/es/zh/ja/de/fr) | модели сделаны под русский и казахский |
| Транспорт | WebSocket, `audio/pcm` 16/24 кГц, `audio/pcmu` 8 кГц | WebSocket, только `audio/pcm`; mu-law перекодируется в `app/live/g711.py` |
| Инструменты | делегирование на бэкенд-модель (`gpt-5.6-luna`) | function calling в самой модели |
| Ключи | `OPENAI_API_KEY` | `YANDEX_API_KEY`, `YANDEX_FOLDER_ID` |
| Голоса | 13 (`marin` по умолчанию) | голоса SpeechKit (`dasha`, `alena`, `filipp`, ...) |

Цены и результаты живых проверок: `docs/NOTES.md`.

Голосовая модель не всегда вызывает `book_meeting` и может ошибиться с днём недели, поэтому после каждого реального звонка работает разбор по транскрипту (`app/services/analysis.py`, `POST_CALL_ANALYSIS=true`): YandexGPT или `BACKEND_MODEL` OpenAI извлекает встречу с датой, итог и просьбу не звонить и дописывает то, что не записали инструменты. Разбор идёт фоновой задачей после финализации звонка: сокет его не ждёт, при остановке приложения задачи дожидаются с таймаутом.

Подключение Яндекса: зарегистрироваться на aistudio.yandex.ru (вход через Яндекс ID), нажать "Создать API-ключ" (сервисный аккаунт с ролью `ai.editor` создаётся автоматически), сохранить секрет, взять идентификатор каталога из консоли, записать в `.env` и выставить `VOICE_ENGINE=yandex`. Модуль `app/live/yandex_live.py`, протокол в шапке.

## Интеграция с GPT-Live-1

Модуль `app/live/openai_live.py`. Протокол взят из документации OpenAI (developers.openai.com, guides `voice-websockets?api=live`, `live-conversations`, `live-delegation`, `voice-sip?api=live`) и повторяет официальные примеры Twilio для GPT-Live-1:

- `session.start` с `model`, `instructions`, `audio.format`, `audio.output.voice`, `delegation.responses.{model, instructions, tools}`
- аудио: `session.input_audio.append` / `session.output_audio.delta`
- транскрипты: `session.input_transcript.delta` / `session.output_transcript.delta`
- инструменты: `response.event` → `response.output_item.done` с `function_call`; ответ через `response.item.create` + `response.create`
- закрытие: `session.close` → `session.closed` с `usage.seconds`

Транскрипты приходят автоматически фрагментами ~200 мс. Модель не говорит первой и ждёт реплики абонента. Исходящие SIP-звонки через `/v1/live/sessions` OpenAI не поддерживает, поэтому используется Twilio Media Streams, а не SIP-коннектор OpenAI. Что не проверено на живом трафике, см. "Известные ограничения"; даты проверок в `docs/NOTES.md`.

Инструменты агента (function calling): `book_meeting(datetime, contact_phone, messenger, comment)` пишет встречу в БД и отмечает цель достигнутой; `mark_do_not_call` переводит все контакты с этим номером в `do_not_call`; `report_outcome(outcome, summary)`; `find_offer` запрашивает оффер у внешнего сервиса; `end_call`.

## Системный промпт

Генерируется в `app/prompts.py` из полей агента. Всегда добавляются правила: говорить только по-русски; на прямой вопрос честно отвечать, что агент виртуальный ассистент, и не выдавать себя за человека; по просьбе не звонить вежливо завершить разговор и пометить номер "не беспокоить"; при договорённости о встрече вызвать `book_meeting`; перед прощанием вызвать `report_outcome` и `end_call`.

## УТП из внешнего сервиса офферов

Персональное предложение под лида берётся из внешнего сервиса по HTTP API:
`GET {OFFERS_URL}/utp/match?budget=&rooms=&district=&metro=&motive=` → `{best, blocks, collections}`.
Волна берёт из ответа только `best` и ровно шесть полей контракта `UtpOffer`: `jk_name`, `title`,
`price_or_threshold`, `condition`, `theme`, `distance_hint`. Остальные поля (`source`, `url`,
`fetched_at`, `score`) отбрасываются в клиенте (`app/services/offers_client.py`), чтобы не могли
попасть в промпт.

Правило честности: агент произносит только эти шесть полей, причём название ЖК модели не
показывается вовсе (оно остаётся в базе звонка для коллеги). Нет оффера (`best: null`, таймаут,
сбой сети) – агент говорит общими словами и ничего не выдумывает. Это прописано в промпте и
покрыто тестами.

Как это работает по времени:

1. Воркер запрашивает УТП **до набора номера**, по данным контакта из базы номеров, и кладёт ответ в
   звонок (`calls.utp_offer`). В разговоре запроса нет, пауза не появляется. Таймаут 2 с.
2. Если клиент назвал другой бюджет, комнатность или район, агент вызывает функцию `find_offer`.
   Таймаут 0.4 с, при срыве разговор идёт дальше без УТП.
3. Сокращения разворачиваются для речи: "от 8,2 млн, 2-к.кв" в "от 8 миллионов 200 тысяч рублей,
   двухкомнатная квартира", "3Е-к.кв" в "евротрёшка, две спальни и кухня-гостиная", "ПВ 15%" в
   "первоначальный взнос 15 процентов", "от 4,3%" в "ставка от 4,3 процента".

Откуда берутся бюджет, комнатность и гео: из CSV базы номеров. Обязательна только колонка `phone`,
остальные необязательны: `name`, `district`, `metro`, `budget`, `rooms` (русские заголовки тоже
понимаются). Чего нет в файле, то выясняет агент в разговоре. Если гео неизвестно, подбор идёт по
бюджету и комнатности.

Адрес сервиса в `OFFERS_URL`. Пусто – волна работает без УТП и в сеть за офферами не ходит вовсе.

## Время в панели и перебивание

Время в базе хранится в UTC, панель показывает его в рабочей таймзоне из `DISPLAY_TIMEZONE`
(по умолчанию Europe/Moscow). Без этого встреча, о которой агент договорился на 12:00 по Москве,
читалась в карточке как 09:00.

Перебивание: провайдер телефонии играет присланные кадры подряд, поэтому при речи клиента очередь
нужно сбрасывать, иначе агент доигрывает фразу поверх собеседника. Волна считает незаигранный
хвост сама (`app/web/playback.py`) и шлёт Twilio сообщение `clear`. Явного события о перебивании
у GPT-Live в документации нет, поэтому сигналом служит транскрипт речи клиента и порог
`BARGE_IN_CLEAR_SECONDS`: короткие поддакивания фразу агента не рвут. У Яндекса есть прямое
событие, ему верим сразу.

## Лимиты площадки и темп обзвона

Площадки объявлений ограничивают число звонков с одного номера в сутки; значение ставится в
`DAILY_CALLS_PER_NUMBER` (0 = без лимита). Счёт идёт по календарным суткам рабочей таймзоны, а не
по UTC, и по нашему номеру (`calls.from_phone`), а не по кампании: номер общий для всех кампаний.
`MIN_SECONDS_BETWEEN_CALLS` задаёт паузу между звонками с одного номера. Логика в
`app/services/quota.py`: воркер резервирует слот на каждый звонок в `number_daily_usage`
(`reserve_daily_slot`), в той же транзакции, что и claim контакта; `count(*)` по звонкам остаётся
для отчётов.

Когда номеров станет несколько, ротация ложится сюда же: остаток считается по каждому номеру
отдельно, потому что записан в звонке.

## Design decisions

1. Интерфейсы и моки. У каждого внешнего контура есть интерфейс и мок-реализация: `LiveSession` (`openai_live`, `yandex_live`, `fake`), `TelephonyProvider` (`twilio_provider`, `fake_provider`), клиент офферов с пустым `OFFERS_URL`. Мост и сервисы видят только нормализованные `LiveEvent`, поэтому сквозной сценарий прогоняется без сети и секретов, а тесты подменяют фабрику сессии, а не патчат протокол. Мок сообщает о себе явно (`LiveSession.supports_analysis`), прод-код не проверяет `isinstance`.
2. Статусы звонка только вперёд, переходы атомарны. `set_call_status` продвигает статус по порядку `queued < ringing < in_progress` одним `UPDATE ... WHERE status IN (<не старше нового>)` (compare-and-set) и не трогает терминальные; терминальный ставит только `finalize_call`: `UPDATE ... WHERE status NOT IN (<терминальные>) RETURNING`, и контакт (done, повтор через `next_attempt_at`, failed, do_not_call) меняется в той же транзакции только у того вызова, который перевёл звонок. Поэтому teardown сокета и status callback Twilio, пришедшие одновременно, дают ровно один переход; проигравший лишь уточняет длительность: у провайдера она точнее. Идемпотентность держится на условии в SQL, а не на чтении перед записью, и верна и для параллельных вызовов. Терминальный статус определяет итог моста (`bridge_outcome`): ошибка без единой реплики это `failed`, разговор с репликами это `completed`, ошибка остаётся в `call.error`.
3. Inbox вебхуков. Twilio шлёт события статуса отдельными запросами, повторяет их и не гарантирует порядок. Каждое событие сначала пишется в `call_events` через `INSERT ... ON CONFLICT DO NOTHING` по ключу (`provider`, `provider_event_id`): заголовок `I-Twilio-Idempotency-Token`, иначе `CallSid:SequenceNumber`, иначе `CallSid:CallStatus`. Повтор (вставка не прошла) отвечает 204 и не обрабатывается; событие с чужим `CallSid` для звонка, у которого `provider_call_id` уже записан, отвечает 400. Входящий звонок создаётся get-or-create по (`provider`, `CallSid`) под частичным уникальным индексом `calls(provider, provider_call_id)`. Inbox это фильтр дублей, не транзакционный outbox: запись события и его обработка (`finalize_call`, `set_call_status`) идут отдельными транзакциями, при падении процесса между ними событие теряется, страховка это `_expire_stuck_calls` воркера.
4. Claim контактов через `FOR UPDATE SKIP LOCKED`. Проход воркера по кампании это одна транзакция под блокировкой строки кампании (`SELECT ... FOR UPDATE`): статус кампании перечитывается под блокировкой, активные звонки считаются там же, кандидаты берутся `SELECT ... FOR UPDATE SKIP LOCKED`, для каждого в той же транзакции проверяется пауза между звонками и резервируется суточный слот номера, контакт переводится в `calling` (`attempts + 1`), звонок создаётся в `queued`; один коммит. Второй экземпляр воркера на той же базе ждёт на строке кампании и видит уже занятые слоты, а по той же базе номеров пропускает заблокированные строки. Сетевой вызов провайдера (`_launch_call`) идёт после коммита: держать блокировку поверх сети нельзя. На SQLite (только тесты) диалект игнорирует `FOR UPDATE`, блокировок строк там нет; это режим одного процесса.
5. Квота номера через `ON CONFLICT`. Суточный лимит звонков с номера резервируется одним оператором `INSERT INTO number_daily_usage ... ON CONFLICT (from_phone, day) DO UPDATE SET used = used + 1 WHERE used < :limit RETURNING used`; пустой результат это отказ. База блокирует строку, два параллельных резервирования не пройдут оба на последнем слоте. Синтаксис у PostgreSQL и SQLite одинаковый, но в SQLAlchemy конструкции разные, поэтому `db.dialect_insert` выбирает её по диалекту сессии.
6. Инварианты в схеме, а не только в коде (миграция 0006). Частичный уникальный индекс `calls(contact_id) WHERE status IN (queued, ringing, in_progress)`: один активный звонок на контакт. `UNIQUE(provider, provider_call_id)` (частичный, `IS NOT NULL`): один звонок провайдера на запись. `UNIQUE(meetings.call_id, scheduled_at)`: повторный `book_meeting` возвращает уже записанную встречу. `CHECK`: окно часов кампании `0 <= start < end <= 24`, `max_concurrent` 1..20, `attempts >= 0`, `rooms` 0..7, `duration_seconds >= 0`. Индексы под реальные запросы: `contacts(list_id, status, next_attempt_at)` для выборки воркера, `calls(campaign_id, status)` для слотов, `calls(from_phone, created_at)` для квоты и паузы, `calls(status, created_at)` для зависших звонков, `contacts(phone)` для "не звонить", и индексы на все внешние ключи. Каскад `contact_lists -> contacts` делает база (`ondelete=CASCADE`, `passive_deletes`), в SQLite для этого включён `PRAGMA foreign_keys=ON`. Соответствие моделей и миграций проверяет `alembic check` в CI.
7. Границы транзакций. Сервисы в `app/services` открывают собственную сессию БД на операцию, потому что вызываются из фоновых задач (воркер, медиа-сокет, разбор), а не только из HTTP-хендлеров; HTTP-хендлеры панели получают сессию через `Depends(get_session)` и коммитят сами. Результаты инструментов агента (`handle_tool_call`) коммитятся на каждый вызов: модель получает ответ только после записи. `goal_achieved` пересчитывается из фактов в базе (`call_results.recompute_goal`), а не из слов модели.
8. Один жизненный цикл звонка поверх WebSocket. `app/web/call_session.run_call_session` общий для Twilio и браузерного стенда: сессия заканчивается, когда завершилось любое из двух (абонент положил трубку или мост закончил, штатно либо с ошибкой), teardown один: остановить мост, дождаться его с таймаутом, положить трубку, финализировать по итогу, запустить разбор фоновой задачей с хранимой ссылкой (`calls._POST_CALL_TASKS`), которую lifespan дожидается при остановке.
9. Аутентификация медиа-сокета. Медиа-сокет Twilio и сокет стенда открываются без cookie панели, поэтому соединение подтверждает токен `app/security.media_token`: HMAC-SHA256 на `SESSION_SECRET` от идентификатора звонка (для Twilio) или `browser:{agent_id}` (для стенда). Twilio получает токен в TwiML `<Parameter name="token">` и возвращает в `start.customParameters`; стенд берёт его со страницы и передаёт в query. Неверный токен закрывает сокет кодом 1008 до создания моста и без изменения статуса звонка. Поэтому в реальном режиме `SESSION_SECRET` обязателен и проверяется при старте. У панели собственной аутентификации нет, токен стенда защищает только от открытия сокета в обход страницы; панель ставится за reverse proxy с авторизацией.
10. Закрытие сессии без утечек. `events()` реальных клиентов отдаёт `closed` из `except` и после штатного конца цикла, но не из `finally` (yield в `finally` ломает `aclose()`), а транспорт закрывается в `finally` через `asyncio.shield`. Мост в своём `finally` зовёт `terminate()` сессии: если `start()` упал уже после подключения, соединение не остаётся висеть. `terminate()` идемпотентна.
11. Что считается известным ограничением. Всё, что не проверено на живом трафике или сознательно не реализовано, перечислено ниже, а не в TODO по коду: список один, и по нему видно, чего ждать от системы.

## Известные ограничения

- Несколько экземпляров воркера на одной базе не дублируют звонки (claim под блокировками, см. Design decisions), но `ACTIVE_BRIDGES` и остановка кампании (`hangup_active_calls`, `_expire_stuck_calls`) видят только мосты своего процесса: звонок, который ведёт другой экземпляр, остановится по таймауту, а не сразу.
- Inbox вебхуков отбрасывает повторы, но не делает обработку транзакционной: падение процесса между записью события и обработкой теряет его, страховка это таймауты воркера.
- Нет аутентификации в панели: ставить за VPN или reverse proxy с авторизацией. Токен сокета стенда (`/test/call`) выдаётся страницей и не заменяет аутентификацию.
- Нет детекции автоответчика (Twilio AMD, `machine_detection="Enable"`, платная опция), нет записи аудио.
- Статус `do_not_call` хранится на контактах; глобального списка номеров нет.
- GPT-Live: вызов функций через `response.event` на живом трафике не проверен (в пробе инструменты не вызывались). События о перебивании агента клиентом в документации нет; full-duplex модель сама прекращает говорить, но уже отправленные в Twilio кадры доиграют, поэтому сброс очереди идёт по транскрипту и порогу. Сигнала окончания речи нет: после `end_call` мост ждёт фиксированную паузу, чтобы модель договорила прощание.
- Yandex Realtime: не проверено, поддерживает ли модель `rate=8000` для телефонии (сейчас mu-law перекодируется в PCM 8 кГц). При обрыве посреди звонка переподключения с восстановлением контекста нет. События закрытия с usage нет: длительность считаем сами.
- Медиа-поток Twilio, закрывшийся до события `start`, финализирует звонок как `failed`: разговора не было.
